# 4read — єдиний виняток з обмеження браузера debug-збірками для явних дверей

v1.3.7 зробила 4read релізним джерелом: сторінка книги та її аудіо
відкриваються лише після проходження сесії вбудованого браузера, тож
відновлення вже імпортованої книги (`browserDestinationFor` для 4read →
`IN_APP_BROWSER` у release) працює через ту саму механіку. Але HTTP-пошук
4read на пристрої нестабільний: Cloudflare ставить челендж, який
OkHttp-клієнт програє, а WebView з реальним браузерним ідентитетором
проходить. У release без пошукової двері через браузер користувач не може
ані знайти 4read-книгу, ані відновити вже імпортовану.

## Рішення

1. 4read — єдине WebView-pattern джерело release-збірки. Усі явні двері
   вбудованого браузера для 4read (`browserDestinationFor` →
   `IN_APP_BROWSER` без умови `isDebug`) відкриваються у release. Це
   розширення ADR-0026, не ревізія: той самий seam, та сама cookie-політика,
   той самий recovery-механізм.
2. Sluhay та sluhayknigi лишаються WebView-pattern джерелами лише в debug,
   як і раніше. Деталізація існуючого рішення, не нове зобов'язання:
   їхній «Відкрити на сайті» у release йде в системний браузер
   (`BrowserDestination.SYSTEM_BROWSER`). Причина — для них немає
   релізного потоку: HTTP-пошук поки працює, відновлення не потрібне,
   Cloudflare-челендж не блокує базовий сценарій.
3. Усі пошукові двері 4read у release ведуть у вбудований браузер — і
   майбутні пошукові CTA для 4read теж. Жодна з цих дверей не запускається
   автоматично — це завжди дія слухача.
4. Політика cookie-ізоляції (#427) не змінюється. 4read first-party
   cookies живуть лише у durable jar WebView, ніколи не потрапляють у Room,
   shared profile, лог, backup, sync або запит на інший host; їх можна
   окремо очистити за явною дією слухача.

## Наслідки

- Слухач release може знайти 4read-книгу навіть коли HTTP-пошук
  заблокований Cloudflare.
- Слухач release може відновити вже імпортовану 4read-книгу після
  проходження браузерної сесії — це працювало вже в #425/#426.
- Sluhay/sluhayknigi не отримують нових release-дверей; обмеження
  браузера debug-збірками тримається як у `BrowserGating.kt`.
- Поява нового релізного WebView-pattern джерела у майбутньому — окреме
  рішення, цей ADR не відкриває прецедент на «всі browser-джерела в
  release».

## Тестовий шов

Існуючий `BrowserGatingTest` уже фіксує виняток для 4read у release та
debug-gating для sluhay/sluhayknigi. Нові пошукові двері додають
ідентичний `IN_APP_BROWSER` expectation — той самий pure-JVM seam, без
потреби Android build variant. Тест на «CTA з порожнього пошуку веде
в системний браузер для не-4read» лишається в силі.

## Відхилені варіанти

- Відкривати вбудований браузер автоматично за першою ознакою
  Cloudflare-челенджу — це прихований side effect, який порушує ADR-0026
  («браузер не запускається автоматично»).
- Зробити всі WebView-pattern джерела релізними — sluhay/sluhayknigi не
  мають релізного потоку, це розширило б attack surface без потреби.
- Використовувати публічний CORS-проксі для 4read-пошуку — суперечить
  privacy-позиції (спека 38) і не дає гарантії проходження челенджу.

## Уточнення 2026-09-13: 4read не має браузерної двері, і двері — останній засіб

Рішення зафіксовано після розбору реального випадку на пристрої: книга SoundBooks
(`seed-soundbooks-19feec66` «Темна матерія», `seed-soundbooks-eaf94ba5` «Про горобця
славного молодця») грала **52-секундну скам-рекламу 4read** замість книги.

**Доведений ланцюг:**
1. трек SoundBooks віддається CDN `arch.sound-books.net` **лише зі своїм Referer**
   (заміряно: без Referer — `403 text/html`; з правильним — `200 audio/mpeg`,
   51 021 112 байт ≈ 53 хв);
2. без правильного Referer — **403**;
3. замість чесної відмови слухач отримував контент 4read;
4. у «Темній матерії» **всі 15 глав мали `durationSeconds = 52`** — це тривалість
   рекламного ролика, а не книги.

**Правила (чинні):**
1. **4read більше не використовує механізм браузерної двері взагалі.** Механізм
   лишається для **інших сервісів під Cloudflare**. У коді це
   `SmartRetryPolicy.browserDoorSourceIds`, який відсіює `SourceRegistry.scamIds()`
   (4read — scam-джерело, ADR-0037/ADR-0041 §9).
2. **Браузерна двер є лише останнім засобом** — вона потрібна **тільки якщо не
   вдалося знайти прямий фолбек-кандидат** (alternate Direct тієї самої Edition).
   Порядок лишається ADR-0026/ADR-0041: local → current Direct → alternate Direct
   → **і лише потім** browser.
3. **Невдача стріму падає чесно** (ADR-0014, «ніколи не вигадувати»): `403` не має
   права сам відкривати жодну web-поверхню; браузер — *declared fallback*, ніколи
   не side effect (ADR-0026).
4. **Регресійний тест:** `BrowserDoorExclusionTest` — 4read не отримує двері навіть
   серед інших джерел; DIRECT-джерела двері не отримують.
