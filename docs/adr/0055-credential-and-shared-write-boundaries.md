# Облікові дані й авторство перевіряються на межі довіри

Перевірка безпеки 2026-10-03 знайшла дві помилки в попередніх рішеннях.
Публічний `device_bindings/{ANDROID_ID}` розкривав і шифротекст коду
відновлення, і вхід ключа, яким його зашифровано. Для читача бази це не
захист. А App Check та наявність Auth-сесії не доводять авторство добірки,
голосу або скарги. Клієнт можна змінити.

## Рішення

1. Публічне відновлення профілю через `device_bindings` скасовано.
   Застосунок не пише й не читає ці записи. Правила відмовляють усім
   клієнтам, включно зі старими версіями. Чинними лишаються локальна
   резервна копія на тому самому пристрої та явний Recovery Code.
   Перевстановлення без них створює новий профіль. Це замінює другий
   шар відновлення з ADR-0021.
2. Ідентифікатор пристрою не називаємо секретом. Локальний
   `DeviceBindingCipher` лишається сумісним із резервними копіями;
   його захист обмежений читачем, якому невідомий ANDROID_ID. Збій
   шифрування ніколи не записує відкритий пароль. Старий відкритий
   пароль зчитується один раз для входу й прибирається зі сховища.
   Нові облікові дані генерує `SecureRandom`.
3. Firestore сам обчислює `sha256(uid)` для автора добірки й
   `sha256(uid + collectionId)` для голосу та скарги. Хеш має той самий
   нижній регістр, що й клієнти. Публічна схема не отримує сирого uid.
   Створення й зміна добірки перевіряють автора; голоси, скарги та їхні
   лічильники перевіряються атомарно через `getAfter`. Зміна книжок чи
   псевдоніма не обнуляє оцінки або модерацію.
4. Одна оцінка чи один відгук не може мати довільні дублікати: правила
   перевіряють канонічний id. Ключ прогресу або Work Relationship
   належить тому самому uid, що й тіло. Кандидат надходження має
   перевірені хеші автора й canonicalUrl та не обходить блокліст.
5. Мережевий транспорт не переносить Cookie, Authorization або Referer
   на інший origin після перенаправлення. Веб-проксі перевіряє кожен
   перехід у межах початкового джерела, приймає лише HTTPS без URL-пароля
   й нестандартного порту та не віддає сторонній HTML як активний вміст.

## Розгортання й обмеження

Зміни в репозиторії не змінюють уже розгорнуті правила. Після перевірки
власник має застосувати їх, прибрати старі `device_bindings` через Admin
SDK і оцінити потребу в заміні потенційно розкритих облікових даних та
відкликанні сесій. Видалення шифротексту не відкликає вже відомий пароль.

`request.appCheck` не є документованим полем Firestore Rules Request.
Стару умову тут не послаблено: вона відмовляє в емуляторі й не доводить
перевірку App Check у хмарі. Перевірка атестації належить service
Enforcement у Firebase. Перш ніж замінювати цю умову на чинну Auth-політику,
треба підтвердити Enforcement та протестувати справжні токени. Локальні
тести відкривають цей гейт лише в пам'яті ізольованого емулятора.

Це рішення не гарантує відсутність невідомих вразливостей. Залишаються
перевірка розгорнутого середовища, захист квот публічного API та аудит
нативних бінарних залежностей.
