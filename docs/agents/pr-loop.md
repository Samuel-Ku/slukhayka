# Черга PR та передавання через DSH

Координатор починає кожен раунд із `python3 scripts/pr-snapshot.py`.
Деталі `gh pr view` і логи відкриває для конкретного блокера. Злиття
виконує один узгоджений координатор на PR через `scripts/merge-pr.sh`.

## Спільний стан

GitHub PR comments зберігають head SHA, докази перевірок, знайдені проблеми
та наступного відповідального. DSH може писати туди сам; координатор читає
GitHub без очікування приватного повідомлення від DSH.

Локальна копія цих фактів поза git (наприклад `.worktrees/pr-queue.json`):

```json
{"pullRequests":{"1805":{"head":"FULL_SHA","coordinator":"queue-chat","implementer":"dsh-session","reviews":{"Spec":{"head":"FULL_SHA","status":"in-progress"},"Standards":{"head":"FULL_SHA","status":"pass"}}}}}
```

Стани огляду: `in-progress`, `pass`, `fail`. Запис `pass` додається лише
після фактичного незалежного огляду. При зміні head старі вердикти втрачають
чинність. `in-progress` старого head продовжує займати слот, доки координатор
не підтвердить завершення або зупинку виконавця і не оновить receipt. Перед наступним рішенням координатор оновлює копію з GitHub.
Імена відповідальних — явні ідентифікатори чатів/сесій, не припущення за автором PR.

```sh
python3 scripts/pr-snapshot.py --queue-state .worktrees/pr-queue.json --queue-json /tmp/pr-next.json
```

Вивід називає наступний крок і відповідального; `dispatchReview=true`
пропонується максимум для трьох PR разом з уже активними оглядами. Один PR
з двома оглядачами рахується одним. Координатор резервує слот до запуску
оглядачів і зберігає `in-progress`, потім перечитує snapshot. Один
координатор диспетчеризує цей файл; він не є розподіленим блокуванням.
Завислий огляд звільняється лише після перевірки стану його виконавця.

`check-merge-gate` — привід викликати справжній merge gate, а не дозвіл на
злиття. Snapshot не перевіряє таймлайн labels, незалежність автора receipt,
усі rerun attempts чи незавершений rebase. Це робота незалежного оглядача
та чинних `review-pass.sh`/`merge-pr.sh`. Порожні checks означають невідомість.

## Робота виконавця

DSH готує зміни, тести й PR на доступному воркері за `machines.md` та
`swarm.md`. Коли потрібне незалежне рев'ю, залишає поточний SHA і докази у
PR. Очікування одного PR не зупиняє доступну Android/core роботу. Якщо всі
задачі зайняті або заблоковані, записує точні блокери й чекає зміни стану.
Повторний зелений прогін без нової зміни не є новою роботою.

Координатор сам читає результати й запускає незалежні Spec/Standards
огляди. Новий head вимагає нового вердикту. Після merge перевіряє GitHub
`MERGED` і наявність squash SHA у свіжому `origin/main`, далі бере наступний PR.

## Доставка в DSH

Для окремого завдання відкрий окрему сесію з унікальною назвою. У поточній
сесії надсилай лише уточнення до її задачі. Перевір назву й workspace.

```sh
python3 scripts/dsh_send.py --serial DEVICE --session-title 'Unique task title' --message-file /tmp/message.txt
```

Адаптер працює лише з уже відкритою сесією й printable ASCII. Звіряє точний
UI title, зберігає наявну чернетку, перевіряє введений текст до Send і появу
саме цього тексту в історії після Send. За помилки нічого автоматично не
повторює: спершу перевір історію. Якщо Android-клавіатура змінила текст,
чернетка лишається для виправлення. Для busy/Queue/Steer адаптер відмовляє;
дочекайся безпечної межі або використай підтриманий транспорт із підтвердженням.

Назва не є незмінним ID сесії; перед використанням координатор звіряє
workspace/ID в Session details. Адаптер сам ID не читає. Unicode потребує
іншого перевіреного транспорту. `delivery=visible-in-history` доводить
доставку, `execution=unconfirmed` вимагає окремого доказу: відповіді агента,
зміни Goal або результату в GitHub. Повідомлення Sent саме по собі недостатнє.

## Перенесення heartbeat

1. Прочитай чинну автоматизацію за її ID, збережи інтервал, prompt і notification policy.
2. Створи цільовий чат; дочекайся справжнього threadId і його прийняття координації.
3. Онови наявну автоматизацію з тим самим ID, новим targetThreadId та збереженими полями.
4. Перечитай автоматизацію в інтерфейсі: звір target, ACTIVE і розклад. Якщо API
   повертає лише картку без полів, потрібна перевірка картки; відповідь Updated
   підтверджує лише прийняття зміни. Перший автоматичний запуск підтверджує роботу розкладу.
5. Повідом попереднього координатора про передавання. Поточний merge доведи
   до узгодженої межі; наступні бере лише новий координатор.

Завершений перенос має докази збереження розкладу, цільового чату, ACTIVE,
прийняття координації та першого автоматичного запуску. Відсутній доказ
позначається неперевіреним, а не замінюється успішним API запитом.
