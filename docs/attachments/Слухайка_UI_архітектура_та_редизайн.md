# Слухайка — UI-архітектура та план наведення порядку

> **Мета:** перетворити поточний інтерфейс на зрозумілу, стабільну й масштабовану UI-систему. Документ свідомо концентрується на **візуальній ієрархії, компонуванні, навігації, станах компонентів та трьох головних вкладках**, а не на реалізації логіки.
>
> **Принцип продукту:** застосунок не є «каталогом з плеєром». Це **аудіоплеєр, у якому відкриття наступної книги не заважає слуханню**.

---

## 1. Цільова інформаційна архітектура

### 1.1. Рівень застосунку

У застосунку мають лишитися три рівноправні кореневі вкладки:

| Вкладка | Робоча назва | Відповідає на питання користувача | Основна візуальна роль |
|---|---|---|---|
| **Слухати** | Listen | «Що я слухаю зараз і що слухати наступним?» | Персональний home, listening-first |
| **Огляд** | Explore | «Що є цікавого у каталозі?» | Вітрина та discovery |
| **Медіатека** | Library | «Що вже моє та як цим керувати?» | Власна колекція й інструменти |

**Критично:** вкладки не повинні намагатися виконувати одну роль.

- **Слухати** показує лише персонально релевантні добірки й поточне прослуховування.
- **Огляд** не повинен виглядати як ще одна медіатека: це місце для пошуку, жанрів, підбірок і каталогу.
- **Медіатека** не повинна бути вітриною: пріоритет тут — контроль, фільтрація, імпорт, статуси та локальні файли.

### 1.2. Навігаційне дерево

```text
App root
├─ Слухати
│  ├─ Деталі книги
│  └─ Повний плеєр
├─ Огляд
│  ├─ Пошук / результати
│  ├─ Каталог за добіркою, жанром, автором або виконавцем
│  ├─ Деталі книги
│  └─ Сторінка серії
└─ Медіатека
   ├─ Книги
   ├─ Закладки
   ├─ Статистика
   └─ Деталі книги

Persistent layer над усіма вкладками
└─ Mini-player → Повний плеєр
                     ├─ Розділи (bottom sheet)
                     ├─ Швидкість (bottom sheet)
                     ├─ Таймер (bottom sheet)
                     └─ Закладка (dialog / sheet)
```

### 1.3. Правило глибини

- **Push screen** — коли користувач переходить у новий самостійний контекст: деталі книги, серія, повний список жанру, пошук.
- **Bottom sheet** — коли користувач лишається в тому самому контексті й змінює параметр: швидкість, таймер, вибір розділу під час відтворення.
- **Dialog** — лише для підтвердження або короткого одноразового введення: видалення, назва закладки.

Зараз головна навігаційна логіка загалом правильна: книга відкривається окремим екраном, а розділи з плеєра — шитом. Але вона має бути формалізована, щоб не виникали дублікати: список глав у деталях книги та список глав як шит повинні мати різні ролі.

## 2. Наскрізний UI-каркас

### 2.1. Вертикальна сітка екрана

Кожен кореневий екран має одну й ту саму будову:

```text
[ Status bar / safe area ]
[ Top app bar ]
[ Scrollable page content ]
[ Mini-player — якщо є активне відтворення ]
[ Bottom navigation ]
[ System navigation / safe area ]
```

**Bottom navigation** — постійна, її не можна перекривати scroll-контентом. **Mini-player** завжди розташовується строго над нею та займає однакову висоту на всіх трьох вкладках. Це прибирає враження, ніби він то «картка у списку», то «плаваючий блок».

### 2.2. Рекомендовані розміри й відступи

| Токен | Значення | Застосування |
|---|---:|---|
| Горизонтальний відступ сторінки | 24 dp | Контент, заголовки, списки |
| Відступ між секціями | 32 dp | Між великими смисловими блоками |
| Відступ у межах секції | 12–16 dp | Заголовок → контент, елементи списку |
| Радіус великої картки | 24 dp | Hero, mini-player, featured-картки |
| Радіус звичайної картки | 16 dp | Книги у списках, картки розділів |
| Висота чіпа | 40 dp | Жанри, фільтри, сортування |
| Мінімальна touch-зона | 48 × 48 dp | Усі іконки та кнопки |

Не потрібно давати картку **кожному** елементу. На темному UI надмірна кількість темно-сірих rounded rectangles перетворює екран на візуальний шум. Картка потрібна, коли треба позначити об’єкт як самостійну одиницю або виділити пріоритет.

### 2.3. Семантика поверхонь

| Рівень | Вигляд | Використання |
|---|---|---|
| Canvas | Основний майже чорний фон | Фон екрана |
| Surface | Темно-синьо-сіра поверхня | Hero, mini-player, модальні поверхні |
| Surface subtle | Ледь відмінна від canvas поверхня | Чіпи, secondary controls |
| Outline | Холодна сіро-синя рамка | Контурні CTA, неактивні поля |
| Accent | Теплий amber | Play, активна вкладка, active-filter, progress |
| Destructive | Рожево-червоний | Видалення та лише небезпечні операції |

Amber вже добре працює як брендова дія. Важливо зберегти правило: **помаранчевий означає активність або головну дію**, а не просто декоративний колір. Якщо на одному екрані amber отримують і 5 play-кнопок, і всі чіпи, і заголовки, і теги — головна дія перестає бути головною.

### 2.4. Типографічна ієрархія

| Рівень | Роль | Приклад |
|---|---|---|
| Display | Назва головного екрана | «Медіатека», «Слухайка» |
| Title | Назва книги у hero / деталях | «Трохи ненависті» |
| Section title | Назва змістовного блоку | «Продовжити слухати», «Весь каталог» |
| Row title | Назва книги у списку | «Дорога до світанку» |
| Body | Автор, серія, опис | «Джо Аберкромбі» |
| Meta | Тривалість, джерело, статус | «Залишилось 14 год 5 хв» |
| Label | Кнопка або фільтр | «Завантажити», «Усі» |

Не варто використовувати CAPS LOCK для всіх секцій: «КАТАЛОГ», «ЖАНРИ», «ВЕСЬ КАТАЛОГ» в одному стилі не створюють структуру, а конкурують між собою. Великі секції мають читатися як `Section title`, а технічні маркери — як невеликий meta-label.

## 3. Вкладка «Слухати» — персональний home

### 3.1. Її єдина роль

«Слухати» має давати користувачу найкоротший шлях до аудіо:

1. Продовжити поточну книгу.
2. Повернутися до того, що було відкладено.
3. Вибрати одну доречну наступну книгу.

Ця вкладка не повинна перетворюватися на нескінченний каталог, інакше вона дублює «Огляд».

### 3.2. Рекомендована композиція

```text
Top app bar: «Слухати»                 [пошук / overflow]

Продовжити слухати
┌───────────────────────────────────────────┐
│ [cover]  Назва книги                       │
│          Автор                             │
│          Глава 11 із 65 · 08:49 / 18:01   │
│          [████████──────]                  │
│                                      [Play]│
└───────────────────────────────────────────┘

Нещодавно слухали                              [Усі]
[compact book row]
[compact book row]

Щось коротке
Менше години прослуховування
[horizontal book cards / compact rows]

Для вас / Продовжити серію
[horizontal cards]
```

### 3.3. Hero-картка

Hero — єдиний найбільший UI-об’єкт на екрані. Він має отримати найбільший контраст, найбільшу обкладинку і найочевидніший CTA.

**Що має бути всередині:**
- обкладинка зліва;
- назва максимум у 2 рядки;
- автор в один рядок;
- контекст прослуховування: `Глава 11 із 65`;
- один прогрес-бар та один змістовний time-label;
- велика play/pause-кнопка справа.

Не показувати одночасно: відсоток, elapsed книги, remaining книги, elapsed глави, remaining глави. Для hero достатньо `Глава 11 із 65 · залишилось 14 год 5 хв`. Детальну подвійно-прогресивну інформацію варто лишити для повного плеєра.

### 3.4. Секції після hero

- Обмежити кількість секцій на стартовому екрані до **4–5**, навіть якщо бекенд здатен віддати більше.
- Один і той самий твір не повинен бути видимим у hero і в першому рядку «Нещодавно слухали» одночасно.
- У секції «Щось коротке» прибрати постійний `X` з кожного рядка. Дії персоналізації потрібно перенести у overflow або swipe-to-dismiss; рядок має лишати головним play.
- Сирі назви від джерел не можна показувати в UI: це не «контент», а дефект даних. UI має отримувати нормалізований `displayTitle`.

## 4. Вкладка «Огляд» — discovery без дублювання

### 4.1. Проблема поточного компонування

На поточному екрані поспіль стоять:

```text
КАТАЛОГ → TOP 100 / Виконавці / Автори
ЖАНРИ → Казка / Вірші / Роман / …
ВЕСЬ КАТАЛОГ → Спочатку нові / За назвою / Усі джерела
                 Усі жанри / Казка / Вірші / Роман / …
```

Другий ряд жанрів дублює перший. Через однакову капс-типографіку секцій не зрозуміло, чи це два різні рівні навігації, чи повторення фільтра. Користувач не має витрачати когнітивне зусилля, щоб вгадати це.

### 4.2. Цільова композиція

```text
Top app bar: «Огляд»                       [пошук]

Швидкий перегляд
[ТОП 100] [Автори] [Виконавці]

Популярні жанри                              [Усі жанри]
[Роман] [Жахи] [Пригоди] [Драма] …

Підбірка: Нове у каталозі                    [Усі]
[horizontal book cards]

Весь каталог
[🔍 Пошук у каталозі]
[Усі жанри ▾] [Нові ▾] [Усі джерела ▾]

N книг
[flat catalog rows]
[flat catalog rows]
```

Тобто жанр існує у двох різних режимах, але не дублюється в одному вигляді:

| Місце | Роль | Вигляд |
|---|---|---|
| «Популярні жанри» | Навігація в discovery | Невеликий горизонтальний ряд чіпів; тап відкриває genre page |
| «Весь каталог» | Фільтр поточного списку | Один filter-chip `Усі жанри ▾`, що відкриває sheet / menu |

### 4.3. Різні типи елементів

В Огляді повинно бути три візуально різні типи контенту:

1. **Navigation tile** — ТОП 100, Автори, Виконавці. Це двері в окремі екрани, а не фільтри. Їм корисні іконка, назва та окрема плиткова форма.
2. **Curated book card** — горизонтальна картка для добірок. Вона має показати обкладинку, назву, автора, коротку метадані.
3. **Catalog row** — компактний рядок масового списку: обкладинка, назва, автор, тривалість/джерела, контекстна дія.

Якщо всі ці сутності візуально — однакові темні картки з трикутником Play, користувач не бачить різниці між «відкрити добірку», «запустити книгу» та «перейти до деталей».

### 4.4. Правила каталожного рядка

```text
[cover] Назва книги                         [⋮]
        Автор
        16 год 41 хв · 2 джерела
```

- Основний tap по рядку — **деталі книги**.
- Play не мусить бути завжди окремою великою кнопкою у правій частині. Для каталогу логічніший overflow або маленький play як secondary-action.
- Наявність `2 джерела` або badge джерела пояснює користувачу, що книга є агрегованою сутністю, а не випадковою копією.
- Довгі назви обрізаються після двох рядків; ніколи не показувати SEO-хвости типу «аудіокнига слухати онлайн українською».

## 5. Вкладка «Медіатека» — інструментальна, але не перевантажена

### 5.1. Роль і порядок пріоритетів

Медіатека відповідає на три питання: що в мене є, де це знайти, як це керувати. Тому її UI має бути щільнішим, ніж в Огляді, але кожен контрол повинен мати чітке місце.

### 5.2. Рекомендована структура

```text
Top app bar: Медіатека                       [⋮]

[+ Додати аудіо] [Папка]

[Книги (63)] [Закладки (1)] [Статистика]

[🔍 Пошук у медіатеці]

[Усі] [Слухаю] [Завершені] [Завантажені]  → горизонтальний скрол

Нещодавно слухані ▾                          [list/grid]
63 книги · 0 завантажено

[Library book row]
[Library book row]
```

### 5.3. Верхня зона

- Не потрібно повторювати великий заголовок, дрібний опис і дві широкі кнопки у два рядки, якщо вертикальний простір дорогий. На малому екрані достатньо: `Медіатека` + overflow, нижче один ряд primary/secondary CTA.
- **«Додати аудіо»** — заповнена primary button.
- **«Папка»** — контурна secondary button.
- Таби `Книги / Закладки / Статистика` повинні бути саме табами: active indicator має бути під елементом, а не змагатися з orange-кнопками у шапці.

### 5.4. Фільтри, сортування, storage

- Фільтри — горизонтально прокручувані, але крайній видимий чіп має мати fade/gradient, щоб жест scroll був очевидний.
- Сортування має бути одним контролом: `Нещодавно слухані ▾`.
- Не змішувати фільтри зі статусом storage.
- Рядок storage — інформаційний, не головний. У разі `0 МБ · 0 офлайн-книг` його краще **не показувати взагалі**, щоб не віддавати висоту нульовому стану.
- Кнопку `Очистити` не можна показувати як непомітний текстовий лінк поруч із storage: дія фізично видаляє аудіо. Показувати її тільки коли є що очищати, та після тапу відкривати confirm-dialog.

### 5.5. Рядок книги в бібліотеці

```text
[cover] Назва книги                         [⋮]
        Автор
        Серія · Книга 1
        [████████────]  Залишилось 14 год 5 хв
        [4read]  /  [Завантажено]
```

У бібліотеці статус важливіший, ніж у каталозі. Тут доречні progress-bar, `Залишилось`, офлайн-ознака та source-badge. В Огляді ці елементи в такому обсязі не потрібні.

## 6. Деталі книги, mini-player і плеєр

### 6.1. Mini-player

Mini-player — головний persistent-компонент застосунку. Його правила:

```text
[cover] Назва книги
        Глава 11                         [pause] [next]
[progress line]
```

- Фіксована висота та однакова форма на всіх вкладках.
- Весь лівий блок відкриває плеєр; pause/next мають окремі touch targets.
- Назва — максимум один рядок, глава — один рядок.
- Progress line має бути заповнена до поточної позиції; стан 0% не повинен бути візуально невідрізним від «даних немає».
- Mini-player не повинен мати надто важку рамку на одному екрані й бути злитим з фоном на іншому.

### 6.2. Деталі книги

Рекомендований порядок блоків:

```text
Top app bar: ← Назва                         [♡] [⋮]

                 [велика обкладинка]
                 Назва книги
                 Автор · Читає …
                 [жанр] [тривалість] [рейтинг]
                 [серія]

[▶ Продовжити] [↓ Завантажити] [🔖]

Про книгу
Короткий опис / дані джерела

Джерела
[source cards]

[Розділи (65)] [Закладки (1)]
[chapter list / bookmark list]
```

**Що прибрати з app bar:** delete. Серце, «відкрити джерело», download, delete в одному горизонтальному ряду створюють ризик помилкового тапу й не мають єдиної частоти використання. У top bar мають бути лише:

- back;
- favorite — якщо це справді одна швидка звична дія;
- overflow `⋮` з: видалити з медіатеки, відкрити у браузері, керувати джерелами.

### 6.3. Повний плеєр

Поточна двошарова модель прогресу є сильною і має лишитися:

```text
[обкладинка]
Назва
Автор · Читає …
Глава 11

Розділ    08:49 / 18:01
[chapter progress]

Книга     02:35:41 / 16:41:11
[book progress]

[previous] [-15] [pause/play] [+30] [next]

[Швидкість] [Таймер] [Закладка] [Розділи]
```

Правила ієрархії:

- `pause/play` — єдина велика кругла акцентна кнопка.
- Prev/next — нейтральні; seek ±15/30 — мають іконку зі стрілкою та цифрою, не просто число.
- Обидва прогрес-бари потрібні, але повинні відрізнятися лейблами й не зливатися: розділ — поточна локальна дія, книга — глобальний контекст.
- Інструменти внизу — однакового візуального рівня; label не обрізається й не перемикає мову.

### 6.4. Розділи: дві точки входу, одна модель

| Контекст | Вигляд | Призначення |
|---|---|---|
| Деталі книги | Вкладка «Розділи» у повному контенті | Огляд структури, прямий старт будь-якої глави |
| Плеєр | Bottom sheet | Швидке перемикання без втрати контексту прослуховування |

Список використовує один `ChapterRow` компонент: номер, назва (якщо є), тривалість, active/played state. Не треба створювати два різних візуальних списки лише через різні точки входу.

## 7. Компоненти та стани

### 7.1. Кнопки

| Рівень | Вигляд | Приклад |
|---|---|---|
| Primary | Amber fill, темний текст | «Продовжити», «Додати аудіо» |
| Secondary | Прозора з outline | «Папка», «Завантажити» |
| Tertiary | Текст / іконка без рамки | «Усі», overflow, back |
| Destructive | Червоний текст у confirm-контексті | «Видалити завантаження» |

На одному екрані — максимум **одна** primary CTA у видимій області. У деталях книги це «Продовжити», а не одночасно «Продовжити», «Завантажити» і «Додати закладку» з однаковою вагою.

### 7.2. Чіпи

Чіп повинен мати тільки один з трьох змістів:

- **Filter chip:** змінює поточний список — `Усі`, `Слухаю`, `Завершені`.
- **Navigation chip:** відкриває новий контекст — `Роман`, `Жахи` у блоці популярних жанрів.
- **Metadata chip:** не інтерактивний — `16 год 41 хв`, `4read`, `4.6`.

Не змішувати їх у один ряд без візуальної різниці. Metadata не повинна виглядати як кнопка, а navigation chip не повинен виглядати як selected filter.

### 7.3. Порожні й завантажувальні стани

UI-порядок руйнується, якщо порожні стани виглядають як зламаний екран.

| Стан | Правильна композиція |
|---|---|
| Немає активного прослуховування | Невелика ілюстрація / іконка, заголовок, CTA «Переглянути каталог» |
| Порожня медіатека | CTA «Додати аудіо» + secondary «Відкрити каталог» |
| Немає результатів фільтра | Текст з активним фільтром + «Скинути фільтри» |
| Книга без глав | Не показувати пустий tab; показати зрозумілу причину у source section |
| Дані ще завантажуються | Skeleton тієї ж форми, що фінальна картка, без стрибків layout |

## 8. План UI-робіт

### P0 — прибрати небезпечне та хаотичне

1. Перенести `Видалити` з app bar деталей книги в overflow-меню.
2. Додати confirm-dialog до `Очистити завантаження`; у тексті показувати кількість книг і розмір даних.
3. Заборонити відображення сирих SEO-заголовків; усі списки використовують нормалізований display title.
4. Уніфікувати локалізацію: прибрати мікс `Playing`, `Download`, `Duration`, `Narrated by` з українського UI.

### P1 — навести порядок у трьох вкладках

1. «Огляд»: прибрати дубль жанрів; залишити верхні жанри як navigation, нижній `Усі жанри ▾` як filter.
2. «Слухати»: обмежити кількість персональних секцій до 4–5; дедуплікувати hero і перший recent-row.
3. «Медіатека»: приховувати storage-zero row; показувати «Очистити» лише за наявності завантажень.
4. Розвести візуально navigation tiles, curated book cards і catalog rows.

### P2 — закріпити дизайн-систему

1. Ввести компоненти `AppTopBar`, `MiniPlayer`, `BookCatalogRow`, `LibraryBookRow`, `ChapterRow`, `FilterChip`, `MetadataBadge`.
2. Винести spacing, radius, colours, type scale до design tokens.
3. Стандартизувати стани: default / pressed / selected / disabled / loading / empty / error.
4. Додати скріншотні UI-регресії на три вкладки, деталку, плеєр і sheet розділів.

## 9. Definition of Done для UI

Роботу з UI можна вважати завершеною, коли:

- Користувач за 1 секунду розуміє різницю між «Слухати», «Оглядом» і «Медіатекою».
- На «Огляді» немає жодного дубльованого контролу без окремої ролі.
- На екрані є тільки одна головна дія, позначена amber.
- Mini-player має однакову форму й положення на кожному root-екрані.
- Всі деструктивні операції вимагають підтвердження.
- Всі тексти однією мовою, усі заголовки нормалізовані.
- Каталог, бібліотека й плеєр використовують різні рядки/картки там, де їхня семантика різна.
- Кожен bottom sheet змінює параметр у поточному контексті, а кожен push screen відкриває новий контекст.
