# Grilling web parity: Web Client 1:1 з Android

Дата: 2026-09-06. Мета: довести Web Client до стану «1 до 1 з Android»,
щоб слухачі на iOS/інших системах мали повноцінний досвід, невідмінний
від застосунку. Метод: grill-with-docs — рішення раундів фіксуються в
`docs/adr/`, спека поставки народжується з останнього раунду.

База: специфікація spec-43 (каркас web, ADR-0023/0024), специфікація v1.4
(ADR-0033: «Web Client успадковує ті самі контракти окремою спекою» —
це вона й є).

## Факти (перевірено кодом, 2026-09-06)

Веб (`web/`, ~9.3k рядків, гілка `release/v1.3.9`) має реальні кістяки:

- 8 адаптерів джерел у воркері поруч із Kotlin-версіями (4read, sluhay,
  sluhayua, lihtar, audiobook-mp3, sound-books, playerjs, LibriVox);
- перевірка доступності (порт Edition Availability Assertion), мовні
  чіпи EN/UA + фільтр мови контенту, Smart Rewind, MediaSession,
  код відновлення + Progress Sync після прив'язки (ADR-0023), uk/en
  словник (~60 ключів) із парністю на рівні типів.

Чого немає (проти Android):

| Поверхня Android | Web сьогодні |
|---|---|
| Слухати — 8 полиць (ADR-0015) | заглушка «ще в роботі» |
| Огляд — полиці, колекції, серії, ТОП 100, персональні рекомендації, жанрові фільтри | плоский фід + пошук + мовний фільтр |
| Медіатека | відсутня повністю (Library Entries живуть лише в Room на Android) |
| Сторінка книги — відгуки, серія, чіпи, обкладинка | розділи + інші начитки + доступність |
| Плеєр — таймер сну, закладки, список розділів | MiniPlayer (54 рядки) + Sheet (49 рядків) |
| Налаштування (мережа, сховище, мови, рекомендації, креші) | лише код відновлення + перемикач sync |
| Індекси (Серії, Колекції, ТОП, Виконавці), сторінки авторів | немає |
| Завантаження / офлайн | немає |
| Вокабулярія v1.4 (PosterCard, BookRow, MetadataChip…) | не застосовується |

Android-таби: `SelectedTab = LISTEN, EXPLORE, LIBRARY, SETTINGS`
(`MainViewModel.kt:111`). Web-таби: `listen, catalog, profile`
(`App.tsx`) — інша структура ще до наповнення.

## Раунд 1 — рішення (прийняті користувачем 2026-09-06)

**R-W1. Визначення «1:1» = паритет поверхонь (варіант (a)).**
Кожен екран і блок Android існує на web з тією самою IA і
вокабулярією компонентів. Механічно неможливе (приватний маршрут
Tor/проксі — ADR-0024, WebView-відновлення 4read — ADR-0026/0027)
фіксується як платформенна дельта в чесному ledger, а не ховається.
Дослівний паритет недосяжний фізично і не є ціллю.

**R-W2. Вокабулярія успадковується з першого дня (варіант «build-on»).**
Web не мігрує власні компоненти, а будує одразу React-еквіваленти
канонічної системи v1.4 (PosterCard, CycleCard, BookRow, MetadataChip,
дворівневі заголовки, два стани, повні ресурси). Міграція двічі
дорожча за одноразову побудову на малому UI (~1.6k рядків).
Рішення зафіксоване в ADR-0034.

**R-W3. Розширення Progress Sync на бібліотеку (варіант (a)) — ADR-0034.**
«Обране» (Library Entries) + tombstones синхронізуються після
свідомої прив'язки; Metadata Overrides — пізніше, окремим тікетом.
Книга, прихована на Android, не має воскресати в Огляді web;
tombstone якориться за Work/mergeKey — так само як covers і reviews.
Це та сама «later spec», яку ADR-0023 записав для Library Entries.

**R-W4. Персональні рекомендації на web = той самий поділ, що Android
(варіант (a)).** Читається той самий серверний Recommendation Profile
за увімкненої Recommendation Participation (ADR-0030/0031); без
участі — локальна адаптація з Listening State браузера. Жодної нової
приватної поверхні; перемикач участі керує тим самим, що і на Android.

**R-W5. Офлайн = streaming-cache першим (варіант (b)).** Service worker
тримає нещодавно слухане доступним офлайн (дослухати поточну книгу без
мережі), без менеджера завантажень у цій ініціативі. Явні завантаження
(OPFS) — окремий тікет після Медіатеки; iOS-виселення сховища робить
їх крихкими саме на пріоритетній платформі.

**R-W6. Еталон верифікації — iOS Safari (PWA), desktop — другий.**
Web існує заради iOS-слухачів (spec-43); саме там першою проявляється
чесність про платформенні обмеження. Кожен тікет закривається
device-перевіреною видимою дельтою (дух ADR-0017).

## Раунд 2 — відповіді (прийняті користувачем 2026-09-06)

**R-W7. Чотири таби 1:1 — Слухати / Огляд / Медіатека / Налаштування.**
`SelectedTab = LISTEN, EXPLORE, LIBRARY, SETTINGS` переноситься дослівно;
«Профіль» перестає бути табом і стає напрямком у Налаштуваннях, як на
Android. До повної поставки проміжні релізи можуть ховати ще порожній
таб, але структура-ціль — саме вона.

**R-W8. IndexedDB — локальна модель web; localStorage лише для дрібних
налаштувань.** Listening State (уже) і Library Entries + tombstones
(нове) живуть у IndexedDB — localStorage в iOS PWA не переживе звільнення
простору браузером. Модель — порт Kotlin-домену (Work / Library Entry /
Tombstone): обидві платформи читають і пишуть однакові строки
синхронізації. Після виселення сховища — чесне повідомлення, не
«порожня Медіатека».

**R-W9. Browser-source двері на web — чесна межа, не емуляція.** На web
грають лише джерела класу DIRECT і UNKNOWN (сторінку парсить воркер,
аудіо direct-first — ADR-0024). Джерело класу BROWSER (4read після
серпня 2026) ніколи не відкривається «десь у фоні»: слухачеві
пропонуються Cross-resolve на прямі джерела (існуючий механізм) і явне
«Відкрити на сайті» поза застосунком із чесним поясненням. Жодних
безшумних емуляцій сесії WebView.

**R-W10. Закладки людей входять у паритет разом із розширенням sync
(R-W3).** Person Bookmarks (обидва ролі, автори й виконавці) портується
на web: ті самі детерміновані id, зберігання в IndexedDB, корисне без
мережі; у Progress Sync входить тією самою поставкою, що й обране —
інакше «Виконавці/ваші закладки» розсинхроняться між пристроями.

## Раунд 3 — відповіді (прийняті користувачем 2026-09-06)

**R-W11. Порядок поставки = драбина «дані спершу» (варіант (a)).**
M0 фундамент (канонічні компоненти + IndexedDB-модель + розширення
sync) → M1 Медіатека → M2 Слухати → M3 Огляд повний → M4 сторінка
книги → M5 плеєр і налаштування → M6 рекомендації + офлайн-кеш.
Медіатека одразу після фундаменту доводить розширення sync на
найменшому UI; далі кожен milestone рендерить уже дзеркалені дані,
а вісім полиць Слухати без них не існують узагалі.

**R-W12. Релізний поїзд = один продукт, одна версія (варіант (a)).**
Перший реліз паритету — v1.5; релізні нотатки несуть дельти обох
платформ, платформенний ledger живе в секції «що не увійшло».
Web не веде власної версії.

**R-W13. Злиття при прив'язці = union через один рядок-ставлення
(варіант (a)).** Ставлення слухача до Work — один рядок зі станом
`entry | tombstone | none`; конфлікти — LWW за серверним часом,
нічиїна виграє tombstone (свідоме приховування не може програти
застарілому обраному). Локальні рядки незв'язаного браузера
зливаються в акаунт при прив'язці. Це подання sync-шару; доменні
поняття Library Entry і Tombstone лишаються як у CONTEXT.md.

**R-W14. Ledger дельт — спека + README (варіант (a)).** Без окремої
in-app поверхні «про відмінності»: чесність керує текстами назовні
(docs/voice.md), а екран не витрачає chrome на те, про що слухач
не питав.

## Статус сесії

Фронтир порожній: усі гілки дерева рішень відвідані — визначення 1:1,
вокабулярія, модель даних, обсяг sync, рекомендації, офлайн, таби,
browser-source двері, закладки людей, порядок поставки, версіювання,
правило злиття, місце ledger. Специфікація поставки —
`docs/specs/2026-09-06-web-parity.md`. Реалізація не починається до
підтвердження спільного розуміння користувачем (правило скіла
grilling).
