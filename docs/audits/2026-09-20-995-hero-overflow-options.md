# #995 — переповнення hero на `fontScale = 2f`: розвідка й варіанти

**Дата:** 2026-09-20 · **Гілка:** `chore/hero-overflow-options-995` · **Статус:** розвідка, рішення за власником. Нічого не виправлено.

Мета: дати варіанти з цінами, а не обрати. Жодного рядка в `app/src/main` не змінено.

## 1. Як зібраний summary — `файл:рядок`

| Що | Де |
|---|---|

| `heroHeight = screenHeightDp * 0.72f` | `BookDetailSections.kt:131` |
| обкладинка, `BoxWithConstraints(matchParentSize)`, `wrapContentHeight(unbounded = true, maxHeight = v1)`, `ContentScale.Crop` | `BookDetailSections.kt:154-178` |
| **контейнер summary: `Column.align(Alignment.BottomCenter)`, `padding(16, 4)`** | `BookDetailSections.kt:209-215` |
| title: `Text`, `maxLines = 2`, `TextOverflow.Ellipsis` | `BookDetailSections.kt:289-301` |
| author: `BoxWithConstraints` → `Row` → `Text` (без `maxLines`) + `PersonBookmarkButton` | `BookDetailSections.kt:303-342` |
| narrator: те саме, `maxLines` немає | `BookDetailSections.kt:343-391` |

| виклик у сторінці: `LazyColumn { item { BookDetailIdentityHeader(...) } }` — **без обмеження висоти** | `BookDetailScreen.kt:780-783` |

**`maxLines` / `TextOverflow` у summary є РІВНО ОДНЕ** — на title (`BookDetailSections.kt:293-294`).
Author, narrator, чипси, universe-рядок і пілюля серії не мають ані `maxLines`, ані
`TextOverflow`, тож **друкарський текст не ріжеться ніколи — він малюється за межі
власного боксу.**

**Що перекриває що.** Перекриттів «бокс на бокс» немає: усі діти — це один `Column`,
і за побудовою вони йдуть одна за одною. Перекриває **намальований текст**, а не
бокс: коли `Text` отримує меншу висоту, ніж його абзац, `Column` кладе наступного
брата одразу під бокс, і абзац першого вилазить на другого. Другий механізм —
`verticalScroll`-контейнер (`Modifier.weight` неможливий), де дитина міряється з
`maxHeight` = залишок і `min` лише опускається під вхідні constraints.

Обкладинка **навмисно** overlay (так задумано в #991 і до нього) — summary завжди
малюється поверх арту. Це не дефект, а архітектура hero.

## 2. Числа переповнення (Robolectric, `w411dp`, `density = 2.625`)

Тимчасовий зонд `Hero995ProbeTest` (видалено до коміту). Продукційний шлях:
`LazyColumn { item { BookDetailIdentityHeader(...) } }`, ширина **411 dp**
(не 320 — на 320 не відтворюється), висота екрана 905 dp (як у кадрі з пристрою).

Вимірювались **два прямокутники на кожен вузол**: бокс (звітує layout, необрізаний
`positionInRoot + size`) і **намальована смуга тексту** (`TextLayoutResult.size.height`,
центрована в боксі).

| fontScale | heroBox | потрібно тексту | дефіцит | висота title (бокс/абзац) | author | narrator | пілюля серії |
|---:|---:|---:|---:|---|---|---|---|
| **1.0** | 651.4 dp | 266.7 dp | **−384.8** | 69.0 = 69.0 | 48.0 / 42.7 | 48.0 / 36.6 | 48.0 |
| **1.3** | 651.4 dp | 289.1 dp | **−362.3** | 70.9 = 70.9 | 54.1 = 54.1 | 49.1 = 49.1 | 53.7 |
| **2.0** | 651.4 dp (`grew=false`) | 457.9 dp | **−193.5** | 92.2 = 92.2 | 75.0 = 75.0 | 105.1 = 105.1 | 105.9 |
| **3.0** | 1227.0 dp (`grew=true`) | 1218.7 dp | **−8.4** | 206.9 = 206.9 | 272.4 | 289.9 | 246.5 |

**Головне, що ці числа кажуть: на продукційному шляху (411 dp) у поточному
коді після #991 накладання НЕ ВІДТВОРЮЄТЬСЯ — ні на 1f, ні на 1.3f, ні на 2f,
ні на 3f.** `heroHeight` вимірюється **не** як 0.72·H, а як висота viewport
LazyColumn (905 dp) — item у LazyColumn міряється з `maxHeight = 818089024 dp`
(нескінченність), hero росте під вміст, `clipToBounds` не ріже нічого.

### Доказ перетину прямокутників — там, де він Є

**На 2f:** «sibling ink overlaps: **0**». Це і є причина, чому #991 «вилікував»
симптом: після нього на 411 dp переповнення немає.

**Єдине перекриття, яке зонд знайшов на продукційному шляху, — на 3f**
(за межами тікета, але показує механізм):

```
scale=3.0 width=411dp parent=LAZY
  narration_rating_row t=850.1 b=936.6 h=86.5
  metadata_chips       t=781.3 b=873.9 h=92.6
  OVERLAP: narration_rating_row ∩ metadata_chips = 23.8 dp tall
```

**Перетини на 2f знаходяться на audit-фікстурі (288 dp контенту =
`Column.width(320.dp).padding(16.dp)`), а не на 411 dp:**

```
scale=2.0 width=288dp  ->  sibling ink overlaps: 0
   (усі бокси мають повну висоту: title 92.2, author 159.6, narrator 179.8,
    chips 67.4, universe 57.9, series 169.9 — разом 750.9 dp, і жоден не стиснуто)
scale=3.0 width=288dp  ->  sibling ink overlaps: 2
   title ∩ universe_line                          =  51.2 dp
   author_link ∩ narrator_link                    = 138.5 dp
   (narrator: бокс 193.5 dp, абзац 470.5 dp -> inkOverflow +277.0 dp)
```

### Чому «живий кадр» показує накладання, а зонд на 2f — ні

Кадр `/home/stealth/tmp/device/549-verified-uk-book-2.0.png` **старіший за #991**:
`UiSurfaceAuditTest` загортає книгу у
`Column(Modifier.width(320.dp).verticalScroll(...).padding(16.dp))`
(`UiSurfaceAuditTest.kt:140`) — тобто **288 dp контенту**, а не 411. На 288 dp
текст переноситься на 3–5 рядків замість 2–3, і сумарна потреба зростає з 457.9 dp
до 750.9 dp — вона перевищує 0.72·H = 651.6 dp задовго до 2f, і саме тому
переповнення видно саме там.

**Перевірка кадру по пікселях** (ImageMagick, маски за кольором):

* помаранчевий текст author («Автор: …», `#E9A13B`) присутній на рядках
  `y = 983…1094` по всій ширині;
* сірі літери `Н`, `О`, `д`, `к`, `з` (це **текст ковер-фолбека** `BookCoverImage`,
  `book.title` + author, `BookCoverImage.kt:165-185`) присутні на тих самих рядках;
* тобто на **≈110 px (≈41 dp) по вертикалі** одночасно намальовані **два різні
  тексти** — «Озвучує: …» і «Автор із довгим подвійним прізвищем» — і вони
  перетинаються по горизонталі.

Додатковий, окремий дефект: `app/src/main/res/drawable/img_neuromancer_cover_1785247475170.jpg`
**не є JPEG** — 492 267 символів U+FFFD, зміщення SOI = −1, файл пошкоджено
UTF-8-конверсією. Тому аудит малює не арт, а ковер-фолбек, і той фолбек сам
накладається на summary. Це не спричинено #995 і не лікується в hero.

## 3. Варіанти

Ціни — грубі оцінки за обсягом і ризиком, не в людино-годинах.

| № | Суть | Ціна | Що з `1f` | Пристрій? | Вплив на доступність |
|---|---|---|---|---|---|
| **A** | `maxLines` + `TextOverflow.Ellipsis` на author/narrator (2 рядки), universe (1), пілюля (2) | мала, 1 файл, ~15 рядків | **байт-у-байт**: на 1f усі тексти вже в межах 2 рядків (author 2, narrator 2, universe 1) — нові межі не спрацьовують | не потрібен (Robolectric 411 dp ловить регресію) | **ПОГІРШУЄ.** Обрізає ім'я саме тому, кому 2f потрібен. Ellipsis на імені автора — це втрата єдиної інформації, яку людина прийшла прочитати. ATF `hasVisualOverflow` стане `false` (обрізання «легальне»), тож тест **перестане ловити** справжню проблему |
| **B** | Прибрати фіксовану стелю там, де вона є, і зняти «72 %» як стелю: дати hero = `wrapContentHeight`, а мінімум лишити | мала, 1 файл, ~5 рядків | **байт-у-байт** на 1f (hero і так 651.4 dp; `grew=false`) | не потрібен | **НЕ ПОГІРШУЄ.** Нічого не обрізається. ### Про варіант «обмежити масштаб тексту»

Cap масштабу тексту в hero («щоб не ламалось») **шкодить людям, яким 2f потрібен**.
Це не «завеликий шрифт» — це **потреба**. `fontScale = 2f` у системі означає, що
людина обрала читати вдвічі більшим; обмежити його в hero — це повернути їй текст,
якого вона не прочитає, і зробити це **непомітно** (виглядатиме як «так і задумано»).
Крім того, це зламає узгодженість: решта сторінки лишиться на 2f, а hero — ні, і
контраст між hero та рештою сторінки читатиметься як дефект верстки.

**Не рекомендувати цей варіант мовчки.** Якщо власник його обирає — це має бути
свідоме рішення з цим текстом перед очима, а не побічний ефект «зробити, щоб не
ламалось».

## 4. Рекомендація

**D як цільовий напрям, B як негайний крок, C — відкинути.**

1. **Негайно — B.** Зняти фіксовану стелю там, де вона є, і лишити мінімум. На
   411 dp це no-op (підтверджено: `grew=false` на 1f/1.3f/2f, перекриттів 0), але
   воно прибирає єдиний механізм, який **усе ще** може народити переповнення —
   bounded-контейнер (як audit-фікстура). 1f лишається байт-у-байт.

2. **Цільовий — D.** Пункт 2 тікета («чи лишається hero overlay-ом») — це і є
   справжнє питання, і саме воно вирішує #995. Доки summary малюється **поверх**
   арту, будь-яке зростання тексту наближає його до верхнього скрайму й до
   тулбара — на 3f це вже видно (перекриття 23.8 dp). Overlay перетворює
   переповнення з «обрізалось» на «налізло на чуже». Якщо hero перестає бути
   overlay-ом, клас дефекту зникає.

3. **C — відкинути.** Вкладений скрол у сторінці, яка вже скролиться, дає другий
   рівень флінгу й невидимий для скрінрідера вміст. Ціна (зміна 1f + пристрій)
   не окупається результатом (нічого не поліпшує для людини з 2f).

4. **A — лише як свідомий вибір власника, не як «безпечний дефолт».** Ellipsis на
   імені автора виглядає як фікс, але відбирає інформацію в того, кому вона
   потрібна, і **вимикає сигнал** `hasVisualOverflow`, яким аудит це ловить.

### Що варто сказати власнику окремо

* **Головний факт розвідки: на 411 dp у поточному коді (після #991) накладання
  на 2f НЕ ВІДТВОРЮЄТЬСЯ.** Переповнення живе на **288 dp** (audit-фікстура
  `Column.width(320.dp).padding(16.dp)`) — саме тому кадр з пристрою його показує,
  а Robolectric на повній ширині — ні. Перш ніж платити за будь-який варіант,
  варто вирішити: **чи 288 dp — це стан, який треба підтримувати** (тоді досить
  B), чи це артефакт фікстури (тоді досить поправити фікстуру на 411 dp і закрити
  тікет без зміни hero).
* Другий, незалежний дефект: `img_neuromancer_cover_1785247475170.jpg` не є JPEG
  (492 267 U+FFFD). Аудит малює ковер-фолбек, і той фолбек накладається на
  summary. **Це варто завести окремим тікетом** — воно псує не лише hero, а й
  усі поверхні, де цей drawable стоїть обкладинкою.
* Другий пункт тікета (сцени `settings` і `navigation` на 2f) цією розвідкою **не
  перевірений** — пристрій недоступний, і крапку тут ставить лише прогін на
  пристрої.

## 5. Додаток: як відтворено

Зонд (тимчасовий, видалено): `Hero995ProbeTest`, Robolectric
`@Config(qualifiers = "uk-rUA-w411dp-h905dp-…", sdk = [36])`,
`@GraphicsMode(NATIVE)`. Продукційний шлях — `LazyColumn { item { … } }`.
Вимірювання — `TextLayoutResult.size.height` (намальований абзац) проти
`positionInRoot + size` (необрізаний бокс). **`boundsInRoot` для цього не
годиться** — він обрізаний вьюпортом (перевірено: дитина 2000 dp звітує 904.8 dp).
