# Перевірка безпеки — 2026-10-03

Перевірено вихідний код Android, веб-клієнт, Worker, правила Firestore,
налаштування TLS/WebView/резервних копій та залежності. Знайдені проблеми
виправлено локально. У консолі Firebase також звірено розгорнуті правила
та режим App Check. Для опублікованого APK v1.4.2 звірено лише checksum
і підпис; для нового підписаного кандидата також зазначені нижче властивості
пакета. Це не гарантія відсутності невідомих вразливостей.

- змінювати спільні кеші та `source_refusal_votes` без авторизації;
- змінювати чужі відгуки й оцінки будь-якому авторизованому клієнту.

Колекція `device_bindings` існує. Її документи та облікові дані не
відкривалися й не завантажувалися. Факт експлуатації не встановлено.
Контрольний повтор перед втручанням 2026-10-03 підтвердив стару версію,
включно з доступом до чужих bindings, прогресу й закладок за самою лише
наявністю Auth-сесії.

Після перезавантаження консоль показала нову активну версію «Today • 5:26 PM»

Це аварійний режим: всі клієнтські записи зупинено, bindings закрито,
приватні читання доступні лише власнику за `uid`, каталог читається.

Синхронізація, нові відгуки, оцінки, надходження та публікації добірок
тимчасово не записуватимуться. Локальне прослуховування лишається.

(потрібна авторизація Firebase CLI; цього разу використано консоль):

відкриті правила як звичайний rollback небезпечно.

## Що ще потрібно перевірити перед висновком про реліз

1. **Розгорнуте середовище.** Firebase-проєкт і попередні небезпечні Rules
   підтверджені вище; аварійні правила застосовано й звірено в консолі.
   Інші локальні виправлення ще не розгорнуто. URL веб-застосунку,
   IAM, секрети Worker, HTTP-заголовки й опублікований APK не перевірено.
2. **Старий App Check-гейт.** `request.appCheck` не є документованим полем
   Rules Request; в емуляторі вираз відмовляє всім таким записам. Його не
   послаблено, щоб випадково не відкрити доступ. Enforcement у продакшені
   вимкнено; потрібні реєстрація застосунків і перевірка справжніх токенів,
   потім чинний gate під конкретний проєкт. Наявність цього виразу не
   доводить attestation. Аварійні правила його не використовують.
   Під час початкової перевірки Android provider не був зареєстрований.
   Під час підготовки відновлення його зареєстровано, API увімкнено за
   підтвердженням власника, публічний ключ збережено для CI. Підписана
   security-збірка успішна в Actions. 2026-10-04 підтверджено справжні
   токени телефона серверними метриками; service Enforcement ще вимкнений.
3. **Потенційно розкриті credentials.** Після закриття читань потрібна
   Admin SDK-перевірка й контрольована ротація паролів/відкликання сесій
   для старих bindings. Просте видалення запису не відкликає пароль.
   Видалення або ротацію продакшен-даних ця перевірка не виконувала.
4. **Квоти та ресурси.** Публічний Worker не має підтвердженого distributed
   rate limit. Локальні межі текстових відповідей додано, але Worker ще не
   розгорнуто. Потрібні ліміти в маршруті й перевірка сумарного бюджету
   дорогих fan-out запитів; 18 секунд застосовується до одного завантаження
   з redirects, а не до всіх послідовних завантажень book-enrichment.
5. **Межі OSV.** Maven-збіги не охоплюють TDLib AAR, native ONNX/CPython,
   вбудований Python-код, сам Android/WebView і build plugins. Відсутність
   CVE-збігу не дорівнює відсутності дефекту. Інструменти в допоміжних
   `scripts/*` npm-проєктах не входили до перевіреного веб-дерева.
   `rules-matrix` перевірено окремо з залишками вище; `duration-cleanup`
   зафіксовано й перевірено окремо (0 npm-збігів). Контрольні суми бінарних
   assets доводять цілісність, а не відсутність вразливостей усередині них.
6. **Локальний backup.** ANDROID_ID-based шифрування не захищає від того,
   хто вже має і backup, і цей id. Для сильнішої гарантії потрібен інший
   контракт відновлення з hardware-backed key або явним секретом слухача.
