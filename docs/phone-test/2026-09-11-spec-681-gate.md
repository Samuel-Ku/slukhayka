# T6 — пристрійна перевірка Source Request Gate (#687)

> Статус: **ЗЕЛЕНИЙ** — усі шість AC підтверджені на пристрої: TTL-читання,
> стрім поза шлюзом, кукі-джерело й «мертве посилання» (404-прогін, AC4,
> 2026-09-19). Розходження 1 — запит холодного старту до скам-джерела
> 4read.org — закрито #812.
> Пристрій: OnePlus 8 Pro (IN2023), Android 14, розблокований, Wi-Fi.
> Збірка: `assembleDebug` з коміту `790ce0f3` (сесія 2026-09-11); AC4-прогін
> 2026-09-19 на тому самому пакеті. Пакет
> `com.slukhayka.audiobooks.debug` встановлено **начисто**
> (`adb uninstall` → `adb install`), тож кеш шлюзу й медіатека порожні.
> Release-пакет із даними слухача не чіпався.

## Метод

Шлюз персистить стан кошиків у `shared_prefs/source_gate_budget.xml`
(`bucket.<host>` = `tokens|lastRefillAtMs`, [SharedPreferencesSourceGateBudgetStore]).
Запис туди відбувається **на кожному допущеному запиті**
(`SourceRequestGate.fetchUnderBudget` → `budgetStore.save`), тому семплінг
файлу через `run-as` дає моменти запитів на хост без root і проксі.
Обмеження: семпл раз на ~0.3 с, а запис із незмінною кількістю токенів
(поповнення компенсувало списання) видно лише як новий стан — тому рахую
*спади токенів* і окремо перевіряю *відсутність змін*. Додатково:
`logcat`, `dumpsys media_session`, витяг Room та WebView-баз.

```bash
adb uninstall com.slukhayka.audiobooks.debug   # справді чистий старт
adb install app/build/outputs/apk/debug/app-debug.apk
# семплінг під час холодного старту / рестарту:
adb shell run-as com.slukhayka.audiobooks.debug \
  cat shared_prefs/source_gate_budget.xml
```

## 1. Холодний старт — PASS (з уточненням)

~37 с. Спади токенів і проміжки **того самого хоста**:

| хост | перший запит, с | списано токенів | проміжки, с |
|---|---|---|---|
| 4read.org | до 1.2 | 1 | — |
| sound-books.net | 2.0 | 5 | 1.6 · 4.6 · 6.1 · 2.7 |
| audiobook-mp3.com | 35.4 | 3 | 0.8 · 0.8 |
| lihtar.in.ua | 37.7 | 1 | — |

- Одночасних запитів до одного хоста немає: послідовні спади токенів із
  джитером 200–800 мс — горло «один у польоті на хост» працює.
- Обхід union/фідів іде **хост за хостом** (`sound-books → audiobook-mp3 →
  lihtar`); сплеску в багато доменів за один момент немає.
- **Уточнення 2026-09-11 (ADR-0039)**: горло пер-хостове, тож критерій «без
  сплеску до багатьох доменів» читається як «один запит у польоті на хост +
  кошик на домен». Глобальної серіалізації з першої редакції ADR більше
  немає — і не має бути (#722/#723).

## 2. Рестарт у межах TTL — PASS

Два рестарти:

- **Рестарт у спокої** (застосунок відкривається на звичайному екрані):
  за ~25 с — **нуль змін бюджету** в усіх 12 хостах, жодного запиту.
  TTL-снапшоти фідів/головної віддають усе без мережі.
- **Рестарт із відновленням плеєра** (попередній стан — плеєр на збої):
  чотири фонові запити `librivox.org 0.5 с · chitaka 6.9 · sluhay 11.9 ·
  sound-books 12.3` — це recovery відновленої сесії (розкид у 12 с, по
  одному на хост), не TTL-читання. Обмежена поведінка; якщо треба тихий
  рестарт навіть із плеєром — окреме рішення.

## 3. Відтворення не гальмується шлюзом — PASS

Імпортовано й відтворено «The Testament» (LibriVox, 29 розділів):
`00:35 / 07:10`, MediaSession `PLAYING`. За 25 с відтворення токени
`archive.org` і `librivox.org` **не змінилися** — стріми йдуть повз шлюз
(окремий playback-клієнт, ADR-0039 §9).

## 4. Мертве посилання — PASS (404-прогін 2026-09-19)

URL глави підмінено на **справді відсутній** шлях того самого хоста
(`…/ac4-404-probe-missing-file.mp3`): `curl` на нього дає **404**, на реальний
трек — **200**. Далі `am force-stop`, прибрано `-wal`/`-shm`, запис залито
через `run-as`.

Результат (`ac4-404-logcat.txt`):

```
Stream playback error      ← рівно ОДИН
re-resolve на реальний URL ← рівно ОДИН
HTTP 206
MediaSession PLAYING
```

Стан БД після прогону: глава знову має **реальний** URL, пробних рядків **0** —
`attemptSelfHeal` спрацював **один раз**, бюджет «один re-resolve на розділ»
дотримано.

Навіщо це окремо від JVM: раніше ланцюг «404 → self-heal → 206» був доведений
лише політикою (`StreamHealPolicyTest` — «the heal budget is one retry per
chapter prepare», `AudioPlayerManagerTest` — «allows one retry only»). Тепер
доведений живий ланцюг і витрата **рівно одного** бюджету.

### Додаткове спостереження 2026-09-11: обрив мережі

Під час відтворення вимкнено Wi-Fi/дані, перехід на наступний розділ:

```
19:20:35 W/AudioPlayer: Stream playback error (ERROR_CODE_IO_NETWORK_CONNECTION_FAILED)
19:20:45 W/HttpFetcher: GET https://archive.org/metadata/testament_2208.poem_librivox failed to connect
```

Одна автоматична спроба (через 10 с), далі чесний стан «Тривалість
невідома», без циклу повторів. Це **не heal-двері**: `StreamHealPolicy` лікує
лише 404/403, а мережевий збій не має коду відповіді — спостережений GET —
інший фоновий резолв.

## 5. Кукі-джерело не відкривається саме — PASS

Після холодного старту, імпорту й відтворення браузерного екрана в стеку
не було. WebView-процес стартує лише для прогріву системного User-Agent
([BrowserIdentity]), сторінка не вантажиться: `app_webview/Default/Cookies`
існує (WebView створює файл), але таблиця `cookies` **порожня — 0 рядків**.
Сесії джерела немає; вердикт доступності лишається локальним.

## Розходження

1. **Холодний старт ходив на 4read.org** (1 запит до 1.2 с) — **закрито
   #812**: `SourceCatalog.fetchCatalogSections` більше не робить запитів на
   4read.org (коментар «#812 — жодних запитів на 4read.org»), секції
   складаються зі знімка й власних потоків застосунку.
2. **«Фон палить бюджет лише при кошику >50%»** у сторі невидимий — класу
   запиту там немає. Політика покрита `SourceRequestGateTest` («a background
   request is skipped while the bucket is at half or less» та «…more than
   half full»).
