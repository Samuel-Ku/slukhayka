# Прийом: перепродування номерів міграцій під час ребейзу на новий main

Дата: 2026-10-06. Привід: ребейз `codex/issue-702-genre-awards` (PR #1160,
зріз 2 #702) на `origin/main` = `c7d80130`. Запис зроблено, щоб наступний
зріз не наступив на ту саму граблю.

## Що трапилось

Зріз #702 писався на базі `670c2436`, де верхня версія БД — **51**. Зріз
добавляв DATA-ONLY міграцію (переприв'язка жанрових заяв під словник
`GenreIdentity`) і займав слот **51→52**: `MIGRATION_51_52` + файл схеми
`52.json` (до-ребейзовий коміт `bac013fa`).

Поки зріз чекав, upstream влив вітринний зріз #704 T6 зріз 2 (`43ecc063`,
PR #1145 — у складі нового main через `c7d80130`), який на ТОМУ САМОМУ
слоті **51→52** додав стовпець `pinnedAt` (зміна схеми, свій `52.json`).
Після ребейзу два різні `52.json` зіткнулись.

Розв'язання — номер перепродано, наш зріз переїхав на **52→53** (коміт
`011540ed`):

- у сирому списку `.addMigrations(...)` білдера `AudiobookDatabase`
  `MIGRATION_51_52` тепер — upstream-ова (`pinnedAt`); наша —
  `MIGRATION_52_53` (`renormalizeGenreClaims`), остання в ланцюжку;
- `53.json` — побайтова копія upstream-`52.json` (різниться лише полем
  `database.version`): міграція data-only, identityHash успадковується
  (`e322c64337ee3d1bb62bf849b242998a` однаковий у 52 і 53);
- до-ребейзовий наш `52.json` за вмістом ідентичний нинішньому `51.json` —
  патерн «data-only міграція копіює схему попередньої версії як свою» тут
  спрацював уже двічі.

## Чому грабля небезпечна

1. **Задвоєння оголошень.** `MIGRATION_51_52` не може існувати двічі:
   ребейз дає конфлікт або компілятор впирається. Це добре, якщо помітити;
   погано, якщо конфлікт «розв'язано» викиданням ЧУЖОЇ міграції — тоді БД
   v51 ніколи не отримає `pinnedAt`, і Room впаде на валідації схеми вже на
   девайсі, а не в CI.
2. **Тихий тест.** Тест, що називає `MIGRATION_52_53`, після перепродування
   може почати перевіряти ВАШУ міграцію там, де автор думав про іншу — або
   навпаки, ланцюжок у тесті не доходить до вашої версії, і ваша міграція
   стає vacuumно непокритою.
3. **Розсинхрон схеми.** Якщо після перепродування ваш `(N+1).json` — не
   копія нового upstream `N.json` (наприклад, лишилась стара), Room бачить
   схему, яку ніхто не мігрував, → crash або тиха invalidation.

## Чек-лист ребейзу з міграцією

**Перед ребейзом**

1. Зафіксуйте свій номер і доказ: `git show HEAD:app/schemas/com.slukhayka.audiobooks.data.db.AudiobookDatabase/<N>.json > /tmp/my-N.json`;
   запишіть трійку (версія N, об'єкт `MIGRATION_(N-1)_N`, ім'я вашої
   внутрішньої функції міграції).

**Після ребейзу — три перевірки**

2. Чи не зайняли слот: `ls app/schemas/…/ | tail` і порівняння вмісту.
   Швидка звірка (поля `version`/`identityHash` не порівнюють — вони
   змінюються легально):
   ```bash
   python3 - <<'PY'
   import json
   S='app/schemas/com.slukhayka.audiobooks.data.db.AudiobookDatabase/'
   def body(p):
       d=json.load(open(p)); d['database'].pop('version',None); d['database'].pop('identityHash',None); return d
   print('data-only:', body(S+'52.json')==body(S+'53.json'))
   PY
   ```
   Чужий `N.json` з ІНШИМ вмістом = ваш номер зайнято → перепродувати.
3. `grep -n "MIGRATION_" app/src/main/java/com/slukhayka/audiobooks/data/db/AudiobookDatabase.kt` —
   ваш об'єкт мусить вести від НОВОЇ верхньої версії main (`N`) до `N+1`
   і бути останнім у сирому списку `.addMigrations(...)`.
4. `grep -rn "MIGRATION_" app/src/test` — кожен тест, що називає ваш номер,
   мусить пінити саме вашу функцію (assert на данинову зміну, яку робить
   ТІЛЬКИ вона: у нас — рядок жанру переїжджає під канонічний id).

**Перепродування**

5. `version = N+1`; об'єкт → `MIGRATION_N_(N+1)`; у список
   `.addMigrations(...)` — після upstream-ового.
6. Якщо ваша міграція data-only: `app/schemas/…/(N+1).json` = побайтова
   копія upstream `N.json` (різниться лише `database.version`). Якщо зі
   зміною схеми — схема ваша, запустіть ksp, щоб згенерувався новий JSON,
   і закомітьте його.
7. Оновіть ланцюжки в тестах до нової версії. Негативний контроль:
   вийміть свою міграцію з ланцюжка — тест вашої міграції мусить ВПАСТИ;
   поверніть. Інакше він пінить чужу міграцію.

**Вибір номера для нового зрізу**

8. Беріть номер від СВІЖОГО `origin/main` (останній `N.json` у
   `app/schemas` на origin/main), не від локального образу main, і перед
   мерджем перевіряйте `git log origin/main --oneline -- app/schemas` —
   слот могли зайняти, поки ви писали.
