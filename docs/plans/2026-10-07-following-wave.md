## Межі цієї передачі

Ціль наступної хвилі — виправити перевірені прогалини й прийняти кожну
через її власний поведінковий критерій. До кінця першої хвилі локальні
копії мають чесний облік і зберігаються після очищення завантажень;
скасування моделі реально припиняє I/O; дослідження жанру дає
спостережений текст джерела або чесні межі негативного результату.

Чинні #487, #524/#525, #620 і #533 залишаються в їхніх виконавців.
Новий агент не бере їх як вільні задачі. Наявність підготовленого тесту,
успішної компіляції або PR не означає виконаного приймання на пристрої.
Наступна хвиля не звільняє їхні claims чи слот збірок.

Найскладніший майбутній зріз — D2. Його production-реалізацію розбито
на три послідовні етапи в секції D2. Передача можлива після рішень
власника; підготовлений D1 повторювати не потрібно. Решта стартових

## Execution Governance

owner_role: чинний координатор до конкретної передачі
agent_sequence: planner → implementer → independent-reviewer → tester → coordinator
required_approvals: готові межі задачі; незалежна рецензія; виконане цільове приймання
max_review_loops: 3
escalation_rule: після трьох невдалих рецензій зафіксувати конкретну причину та передати координатору; не послаблювати критерії приймання

Перед кожною передачею:

1. Повторити fetch main, прочитати issue з останніми коментарями та відкриті PR.
2. Перевірити agent-work-claim.py status у спільному Git common dir.
3. Доставлений зріз прибрати з доручення. Зайнятий передавати лише через власника.
4. Атомарно отримати claim до першої зміни; конфлікт claim зупиняє старт.
5. За чинною авторизацією координації позначити резервування в GitHub перед кодом.
6. Передати один issue одному виконавцю: scope, branch/worktree, база, заборонені файли та критерії приймання.

MainViewModel, MainActivity, PlayerScreen, DAO, схема Room і strings мають
одного writer-а на конкретний інтеграційний зріз. Виконавці готують свої
модулі у відокремлених worktree; доступ до спільних файлів передається явно.
Важкі Gradle-запуски виконуються через один спільний build slot.
Чужі незбережені зміни, резервування й гілки не очищати.

### Контракти ролей

planner_entry: актуальні main/issue/PR/claims прочитані
planner_output: вузький scope, погоджені рішення, тестовий oracle та prompt RESUME_FROM
planner_handoff: implementer після резервування
planner_stop: зайнятий issue або критичне невирішене правило

implementer_entry: конкретне доручення, claim та межі файлів
