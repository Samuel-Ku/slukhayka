# План: #1645 — KDoc LibraryTabsWithSearch описує фактичну умову inline-смуги

Огляд PR #1632/#1637 зафіксував застарілий KDoc над `LibraryTabsWithSearch`:
«At 360–411 dp the row is inline (search 160 dp, never below its 140 dp floor)».
Фактичний код (після #1580/#1617 і #1627):

- inline лише з `maxWidth >= 400.dp` (нижче — той самий дво-смуговий fallback,
  що й 320 dp);
- пігулка пошуку — **140 dp** (`Modifier.width(140.dp)`), не 160;
- з #1627 inline додатково вимагає `3 × widestLabel ≤ maxWidth − 32 − 4 − 140`
  на поточному fontScale; інакше — fallback, і там підпис може переноситися
  (`tabLabelMaxLines = 2`), а не різатися.

## Рішення

Оновити лише KDoc (коментар) над функцією: назвати поріг 400 dp, справжню
ширину пігулки 140 dp, вимір найширшого підпису (#1627) і долю fallback.
Код, ресурси, тести, еталони не змінюються — це виправлення документації,
яка суперечила коду (правило репо: коментар не сильніший за код — і не
слабший: він мусить його описувати).

Спека §5 (`docs/specs/2026-10-26-ui-refresh-2027.md`) уже описує напрям без
«160 dp», тож її не чіпаємо. Інші «160 dp» у файлі (рядок про тайл ~160 dp)
стосуються іншого віджета й лишаються.

## Перевірка

- Змінено рівно один блок KDoc; `git diff` показує лише коментар.
- CI-гейт: компіляція + існуючі `LibraryChromeHeightTest` /
  `LibraryTabsFitTest` (поріг 400 dp, вимір, fallback) — без змін поведінки,
  тож мають лишитися зеленими; еталони не змінюються (рендер не зачеплений).
- Мутація не застосовна: текстове твердження перевіряється читанням проти
  коду (жодного нового поведінкового контракту).
