# Порядок у гілках

Нічний воркфлоу `branch-hygiene` (`.github/workflows/branch-hygiene.yml`)
прибирає те, що вже повністю в `main`, і оновлює звіт про застій. Він біжить
за розкладом (`23 2 * * *`), а руками запускається через `workflow_dispatch`
із `dry_run: true`.

Дві частини роботи розділені навмисно:

- **чистка** — детерміноване рішення скрипта, без моделі;
- **звіт** — факти плюс наратив LLM, який нічого не видаляє.

## Що можна видаляти

Гілку на `origin` видаляє лише доведений факт, що її вміст уже в `main`:

| Доведення | Коли спрацьовує |
|---|---|
| `ancestor` | tip гілки — предок `main` (звичайне злиття merge-комітом) |
| `pr-merged-sha` | PR злито, і `headRefOid` того PR досі дорівнює tip гілки (squash і rebase) |
| `patch-absorbed` | `git cherry main <tip>` не знаходить жодного унікального патча |

`pr-merged-sha` — головне доведення для цього репозиторію: PR тут зливаються
squash-ем, тому tip гілки не стає предком `main`, і `git cherry` бачить ті самі
зміни як нові. Якщо після злиття на гілці з'явилися ще коміти, tip уже не
дорівнює `headRefOid` — така гілка не видаляється, а потрапляє у звіт як
«PR злито, але гілка рухалася далі».

## Що не видаляється ніколи

- `main`, `master`, `HEAD`;
- `legal/*` — правова основа ліцензії;
- `backup/*` — страхові копії, їхня мета саме пережити `main`;
- будь-яка гілка з **відкритим** PR, навіть повністю поглинута;
- `release/*` без тега `v*` на своїй лінії — публікація відбувається push-ом
  тега, тому жодна неанонсована лінія не зникає (див. `RELEASE-BRANCH.md`);
- гілки, які рухалися після злиття свого PR.

Додатковий захист на прогін: `--protect 'wip/*'` (можна кілька разів).

## Звіт

Один відкритий issue «Порядок у гілках — нічний звіт» із лейблом
`branch-hygiene`. Воркфлоу не створює новий issue щоночі, а переписує тіло
наявного (правка issue не будить підписників). У звіті:

- що видалено цієї ночі та що не вдалося видалити;
- гілки без PR;
- злиті PR, чиї гілки лишилися;
- драфти й відкриті PR без руху ≥ 14 днів;
- «що варто зробити» — наратив LLM або детермінований перелік.

Поріг застою — 14 днів (`--stale-days`). Той самий текст дублюється в summary
прогону, тому issue можна не відкривати, якщо прогін стався щойно.

## Наратив LLM

Один виклик на прогін через той самий endpoint, що в `ocr-review.yml`
(`opencode.ai/zen/go/v1`, модель `deepseek-v4.1-flash`). Токен береться з
секрету `BRANCH_HYGIENE_LLM_TOKEN`, а якщо його не заведено — з
`OCR_LLM_AUTH_TOKEN`. Без токена звіт не падає: «що варто зробити» стає
детермінованим переліком, і це чесно написано в тілі.

Модель отримує лише факти (назви гілок, вік, стан PR, останній коміт) і не має
права нічого видаляти: воркфлоу не має кроку, який виконує її поради.

## Руками

```bash
# факти про віддалені гілки та їхні PR
python3 scripts/branch-hygiene.py collect --json /tmp/facts.json

# сухий прогін чистки (типова поведінка без --apply)
python3 scripts/branch-hygiene.py cleanup --facts /tmp/facts.json

# видалити те, що доведено поглинутим
python3 scripts/branch-hygiene.py cleanup --facts /tmp/facts.json --apply

# звіт у stdout, без LLM і без issue
python3 scripts/branch-hygiene.py report --facts /tmp/facts.json --no-llm
```

У CI той самий скрипт запускає `workflow_dispatch` з `dry_run: true`: тоді
нічого не видаляється й issue не оновлюється, а повний звіт видно в summary.

## Межі

Локальні гілки та worktree (`/home/stealth/Projects/slukhayka/.worktrees/`)
воркфлоу не бачить: він біжить на окремій машині GitHub. Їх прибирає
мейнтейнер, орієнтуючись на розділ «Гілки без PR» у звіті. Локальні refи
навмисно не чіпаються ніде — вони можуть нести ще не запушені страхові патчі.

## Тести

```bash
python3 -m unittest scripts.tests.test_branch_hygiene
```

Право на видалення пінить і реєстр сторожів (`scripts/guard_witnesses.py`):
мутація, яка знімає перевірку бази PR, червонить
`test_pr_merged_into_a_release_lane_is_not_proof` у джобі `script-tests`. Тож
твердження «PR, злитий у релізну лінію, не дає права видаляти» відтворюється в
CI, а не тримається на слові.
