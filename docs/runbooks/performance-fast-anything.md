# Заміри обробки каталогу й добірок

## Цикл оптимізації

Адаптація [The sub-50 ms page-load loop](https://signals.forwardfuture.com/loop-library/loops/sub-50ms-page-load-loop/)
із Loop Library для Android: порівнюємо однаковий сценарій до та після
зміни, зберігаємо лише підтверджене прискорення з незмінною поведінкою.
Поріг вебсторінок 50 мс на Android не переноситься.

> За запитом прискорюй Android-код «Слухайки». Перечитай поточний код і
> резервування роботи. За профілем обери вузьке місце, збережи початковий
> замір і внеси одну зворотну зміну. Повтори той самий замір, цільові тести
> та окрему перевірку результатів. Збережи лише підтверджений виграш і
> запиши докази. Продовжуй, доки є вимірюваний прогрес; зупинись без
> виграшу або коли потрібне середовище недоступне. Чужі зміни збережи;
> публікацію чи руйнівні дії погодь окремо.

JVM-замір перевіряє конкретний обчислювальний шлях. Для висновку про
швидкість запуску чи екрана потрібен окремий замір на Android; відсутній
пристрій або емулятор означає брак цього доказу, а не успіх такого заміру.

## Android: зіставлення добірок

`CollectionMatcher` викликається під час оновлення каталогу та повторної
проєкції мовного фільтра в `SourceCatalog`. Він зіставляє списки премій і
живі добірки з творами медіатеки. Записи списків готуються один раз за
виклик; автор твору нормалізується один раз, назва — лише коли є запис
цього автора з конкретною назвою. Підготовлені дані живуть у межах виклику,
тому зміна медіатеки чи добірки відразу враховується.

Повторний JVM-замір із кореня репозиторію:

```sh
python3 scripts/benchmark-collections.py
```

Потрібні Java 21, кешований Kotlin-компілятор із Gradle та наявна debug-
компіляція проєкту. Скрипт перекомпілює поточний matcher, нормалізатори,
декодер списків і сценарій заміру в тимчасовий JAR. Наявні debug-класи
використовуються для решти моделей даних. Він не запускає Gradle й не
змінює результати збірки. Для інших шляхів є `SLUKHAYKA_JAVA_HOME`,
`SLUKHAYKA_APP_CLASSES`, `SLUKHAYKA_KOTLIN_LIB` і `GRADLE_USER_HOME`.

Сценарій використовує справжні JSON-списки премій і синтетичні медіатеки
зі 100 та 1000 творів. Порівняння — з попереднім повним перебором через
публічне правило `entryMatches`. Спочатку перевіряється рівність результатів,
потім обидві версії прогріваються. Дев’ять серій по три виклики чергують
порядок виконання. Вивід містить медіану мілісекунд на виклик та всі серії.
Це час matcher у JVM на комп’ютері, а не час екрана чи запуску на телефоні.

## Android: злиття пошукових результатів

`mergeGlobalSearchResults` об’єднує відповіді джерел для пошуку, каталогу
та новинок. Ключ твору обчислюється один раз для кожного придатного
вхідного запису й повторно використовується для картки та Edition id.
Порожній бібліографічний ключ зберігається окремо від fallback-ключа
групування `sourceId|url`; fallback не стає частиною ідентичності озвучення.

```sh
python3 scripts/benchmark-collections.py --search
```

Передумови та ізоляція компіляції — ті самі, що для добірок вище. Сценарій
використовує назви й авторів зі списків премій у синтетичних відповідях
джерел: 200 різних творів, 1000 різних творів і 1000 записів про 100 творів.
Мережевих запитів немає. Для кожного набору є 100 прогрівальних викликів
і дев’ять серій по десять викликів; вивід містить медіану мілісекунд на
одне злиття та всі серії. Перед зміною коду збережи цей вивід, після —
повтори ту саму команду в тому самому середовищі.

Це JVM-час злиття вже отриманих записів. Час відповіді джерел, пошуку
в базі та відображення карток до нього не входить.

## Web: об’єднання каталогу

[fast-anything](https://github.com/EL4CTEO/fast-anything) знаходить функції,
на які витрачається процесорний час. Для вебкаталогу тут є окремий сценарій
без мережевих запитів: збережені сторінки трьох джерел і синтетичний набір
із 300 карток. Він викликає справжній `mergeWorkFeed` зі збірки поточного коду.

### Встановлення

Потрібні Node 22.12+ і встановлені залежності `web`.

```sh
npm install -g @el4cteo/fast-anything@0.8.6
fast-anything doctor
codex mcp add fast-anything -- fast-anything mcp
```

MCP-сервер стане доступним у новій сесії Codex. CLI можна використовувати
одразу. Для `scan` Rust не потрібен; `doctor` окремо повідомляє, чи доступні
засоби перенесення функцій.

### Замір до й після зміни

Команди виконуються з `web/`. Спочатку збережи збірку початкового коду:

```sh
node scripts/profile-work-feed.mjs prepare
cp .perf-cache/work-feed.mjs .perf-cache/before.mjs
fast-anything scan -- node scripts/profile-work-feed.mjs run
```

Після зміни коду перебудуй модуль і порівняй:

```sh
node scripts/profile-work-feed.mjs prepare
node scripts/profile-work-feed.mjs bench .perf-cache/before.mjs
fast-anything scan -- node scripts/profile-work-feed.mjs run
```

`prepare` зберігає попередню копію `before.mjs`. `bench` перевіряє однакові
результати для різних сторінок і розмірів сторінки, прогріває обидві версії
та чергує порядок дев’яти серій замірів. Вивід містить медіану мілісекунд
на один виклик, співвідношення часу й усі серії. Збережені сторінки та
синтетичні дані мають окремі результати.

Це час об’єднання вже отриманих карток у Node. Мережа, розбір HTML, React,
запуск Android і відтворення аудіо в нього не входять. Профілі `.fast/` та
збірки `.perf-cache/` локальні й виключені з Git. Профайлер шукає функції
у файлах, тому сценарій спочатку створює звичайний ES-модуль замість
виконання об’єднання через віртуальні модулі Vite SSR.

## Межа перенесення у Rust

Версія 0.8.6 використовує Node-API для JavaScript і Java FFM із JDK 22+
для Kotlin/JVM у `src/main/kotlin`. Android-код проєкту лежить у
`src/main/java` й збирається з Java 21. Готовий міст інструмента не є
Android JNI-мостом. Node-API-модуль також не підходить для браузера чи
Cloudflare Worker. Тут fast-anything використовується для профілювання;
оптимізації залишаються у Kotlin та TypeScript і працюють у чинних середовищах.

Підключення іншого нативного середовища — окрема зміна зі своєю збіркою,
перевіркою поведінки та заміром на цільовій платформі.

Щоб прибрати MCP-підключення: `codex mcp remove fast-anything`.
