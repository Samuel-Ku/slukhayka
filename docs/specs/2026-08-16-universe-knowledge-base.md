# [Spec-26] Спільна база знань всесвітів (мінімальним коштом)

> **Status:** Draft — synthesized from the 2026-08-16 grilling; decisions locked with the user.
> **Tracker:** to be filed as issues (labels `spec-26`, `ready-for-agent`).

## Problem Statement

Spec-25 built the series-universe resolution on two layers: a curated asset (4 universes) and a runtime Wikidata provider. The live sanity run exposed three real gaps in the Wikidata path, and the architecture has a structural cost problem:

1. **Uk-лейблів на Wikidata часто немає** — якірний твір «Трохи ненависті» (Q131414129) має лише ru/en лейбли і жодного uk-посилання; пошук за українською назвою його ніколи не знайде.
2. **429-тротлінг пошуку** — бурстові запити з однієї IP отримують 429, а `HttpFetcher` мовчки повертає порожній рядок → резолюція тихо не відбувається.
3. **Пошук лише за назвою** — автор не бере участі в запиті.
4. **Кеш на кожному пристрої** — кожен користувач будує базу з нуля через Wikidata, замість інкрементального росту; існуючі резолюції нікуди не зникають, додаються лише нові книги.
5. **Неможлива ручна верифікація** — каталог >10 000 книг, власник не може перевіряти базу вручну; верифікацію має робити сама система (або спільнота джерела), а виправлення приходити від користувачів.

Головна ціль: **мінімальний кошт** — нуль інфраструктури, нуль оплати за дані, нуль ручної праці після налаштування.

## Рішення (зафіксовані)

1. **Скоуп — лише зв'язки серія → всесвіт** (порядок, precedes/follows). Решта метаданих і так приходить від джерел при імпорті.
2. **LLM не використовується взагалі** — ні як інструмент наповнення, ні в рантаймі. Wikidata — це вже верифікована спільнотою база (P50/P179/P155/P156 перехресно перевірені людьми); LLM вимагав би саме тієї верифікації, яку власник робити не може.
3. **Спочатку вичерпати Wikidata** (чистий клієнт, нуль інфраструктури):
   - fallback-переклад назви uk → ru/en через **ML Kit Translation (on-device)** — офіційна безкоштовна бібліотека Google, без ключа й лімітів, текст не покидає пристрій; модель завантажується один раз на пару мов (бажано Wi-Fi). Підтверджено наживо: ru-пошук «Немного ненависти» знаходить Q131414129;
   - **автор у пошуковому запиті** (title + author токени);
   - **retry з backoff на 429**.
   Після фіксів — **виміряти залишок** на реальному каталозі: скільки книг лишається нерозпізнаними. Це калібрує решту рішень.
4. **Спільний сторедж — Firebase Firestore, безкоштовний тариф** (1 ГБ, 50k читань/день, 20k записів/день; BOM уже в графі залежностей, просто не використовується). Патерн **клієнт-перший**: локальний Room-кеш → Firestore → Wikidata при промаху → запис результату назад. Нуль серверів, нуль операційних витрат.
5. **Модель запису — довірені клієнтські записи з провенансом**: запис містить `source=wikidata`, прапорець «автор зійшовся (P50)» і `resolvedAt`. **Канал фідбеку користувачів**: скарга «невірний всесвіт» → статус `reported` → додаток перестає показувати і перерезолвлює → новий результат замінює старий для всіх; той самий — скарга ігнорується. База самолікується без участі власника.
6. **Розумне планування оновлень** — трьохрівневий TTL на двох сигналах, які вже будуть у кеші:
   - **Сигнал 1 — положення в ланцюгу**: серія — остання у всесвіті (немає `follows`)? Тоді можливе продовження → гаряча; у середині — стабільна.
   - **Сигнал 2 — вік серії**: останній рік публікації творів (P577, захоплюється при резолюції). Стара серія = завершена.
   - **Гаряча** (~7 днів): хвіст ланцюга + серія молодша ~3 років.
   - **Тепла** (~30 днів): хвіст але стара, або свіжа в середині.
   - **Холодна** (~180 днів, підлога): решта — підлога розносить виправлення Wikidata.
   - **Подієвий тригер на імпорті**: нова книга в бібліотеці з серією відомого всесвіту → негайна валідація ланцюга (дешево — кілька рядків). З Firestore це працює на всіх: будь-який користувач імпортує нову книгу → оновлений ланцюг у спільній базі для всіх.
   - Черга = фоновий пас (detached-window ідіома, як duration-проб; WorkManager у проєкті немає), батчами, з тротлінгом нижче порога 429.
7. **Курований ассет лишається як офлайн-сід**: топ-N всесвітів, без росту; при першому запуску підсіває Firestore. Найнижчий пріоритет читання, але гарантія офлайну для топ-N на свіжій установці.

## Архітектура (шлях читання)

```
Room-кеш (миттєво, офлайн)
  → Firestore (спільна база, швидко)
    → Wikidata (при промаху, повільно) → запис назад у Firestore + Room
```

Сід: ассет → Firestore при першому запуску. Виправлення: скарга → `reported` → перерезолюція → заміна.

## Порядок будівництва (окремі тікети, кожен самодостатній)

1. **Фікси Wikidata** (переклад DeepL Free, автор у пошуку, retry 429) + **вимірювання залишку** на реальному каталозі.
2. **Firestore-сторедж**: read-miss-write, провенанс, локальне дзеркало в Room, ассет-сід. Підключення Firebase-проєкту (єдиний «зовнішній» крок — створити проєкт і покласти ключі).
3. **Розумне оновлення**: тіри, P577-вік, подієвий тригер на імпорті, фонова черга.
4. **Канал фідбеку**: скарга → reported → перерезолюція → поширення.

## Модель вартості

- **Firestore free tier** — нуль серверів, 50k читань/день більш ніж достатньо (читання — основний шлях; промахи зводяться до цівки).
- **ML Kit Translation** — повністю безкоштовно, без ключа й лімітів; одноразове завантаження моделі на пару мов (uk→ru, uk→en).
- **LLM** — 0 грн.
- **Власник** — 0 годин після налаштування; виправлення йдуть через користувацький фідбек.

## Out of Scope

- Активний моніторинг 4read («сповіщення про новинки в серіях») — окремий скоуп, потребує нового адаптера та ризикує тротлінгом 4read.
- Ширша база знань (переклади всіх назв, описи, обкладинки).
- Авторські сторінки та всесвіти на рівні авторів.

## Подальші нотатки

- Ідентичність твору для спільної бази — mergeKey (`title|author|narrator`, нормалізований) або id книги 4read; рішення фіксується в тікеті кроку 2.
- Рік серії (P577) захоплюється при резолюції — окреме поле в кеші.
- Скарги перевикористовують наявну таблицю `corrections` (патерн USER_MADE).
