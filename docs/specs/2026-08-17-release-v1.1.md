# Spec-29: Реліз Слухайка v1.1 — перший реліз під `com.slukhayka.audiobooks`

> **Status:** ready-for-agent. Синтезовано з сесії `/grill-me` 2026-08-17: 9 питань,
> усі відповіді за рекомендаціями. Не вимагає нових рантайм-швів; єдиний новий
> шов — артефакт релізу.

## Problem Statement

Слухайка виросла з однопристроєвого прототипу в продукт, яким користуються
10+ людей на різних пристроях. Перший реліз (v1.0) вийшов під тимчасовим
`applicationId = com.aistudio.audiobook.read`; після нього пакет перейменовано
на `com.slukhayka.audiobooks`, а на `main` накопичилось ~40 комітів цінності
(spec-26 всесвіти, spec-28 Огляд/дискавері, spec-27 UX-фікси), якої користувачі
ще не бачать. Реліз-пайплайн досі випускає анонімний `app-release.apk`,
підписує в CI ключем, що не збігається з локальним, не має чейнджлогу і не має
пре-релізного гейта. Потрібен чистий, відтворюваний реліз v1.1 під фінальною
ідентичністю пакета, з чесним поясненням міграції для наявних користувачів.

## Solution

Випустити поточний `main` як **v1.1** під постійним `applicationId
com.slukhayka.audiobooks`, з `versionCode = 2` / `versionName = "1.1"`, APK
`slukhayka-v1.1.apk` (+ SHA-256), підписаним єдиним канонічним ключем
(локальний `my-upload-key.jks`, синхронізований у CI-секрет). Реліз іде через
наявний `release.yml` на тезі `v1.1` і публікує GitHub Release з ручними
людськими нотатками, що містять обов'язковий блок міграції (новий пакет →
прогрес/завантаження не переносяться). Пре-релізний гейт: JVM-тести + lint +
ручний смоук на пристрої фінальним підписаним APK.

## User Stories

1. As a listener with the old app installed, I want the new app to install as a recognisable «Слухайка» next to the old one, so that I understand there are now two apps and one is the new home.
2. As a listener, I want an honest release note that my listening progress, downloads and history do NOT transfer to the new package, so that I am not surprised when I reinstall.
3. As a listener, I want to re-import my books into the new app, so that I can continue listening without losing access to my library.
4. As a listener, I want to know when it is safe to delete the old app, so that I do not keep two audiobook players using storage.
5. As a listener, I want a distinguishable APK filename (`slukhayka-v1.1.apk`), so that I can tell versions apart in my Downloads folder.
6. As a listener, I want a SHA-256 checksum published next to the APK, so that I can verify the file's integrity before installing.
7. As a listener, I want the new app to contain the Огляд/discovery surfaces, the «Серії»/«Колекції» indexes, universe context and the UX fixes, so that I get the value that has been built since v1.0.
8. As a listener on an older Android 7+ device, I want the release to install and run on my device, so that I am not left behind by the minSdk boundary.
9. As a listener, I want the release notes written in human Ukrainian rather than raw commit messages, so that I understand what actually changed.
10. As a listener, I want every future version to install over this one (same signature), so that I never have to reinstall from scratch again.
11. As the maintainer, I want one canonical signing key used both locally and in CI, so that local and CI builds are interchangeable and never hit a signature mismatch.
12. As the maintainer, I want the release built and published automatically on a version tag, so that releases are reproducible and do not depend on the state of my laptop.
13. As the maintainer, I want the APK filename to carry the version, so that artifacts are unambiguous across releases.
14. As the maintainer, I want a pre-release gate (JVM tests + lint + on-device smoke), so that I do not ship a broken build.
15. As the maintainer, I want `versionCode` bumped monotonically, so that Android always treats the next release as an upgrade.
16. As the maintainer, I want a durable backup of the signing keystore and its passwords, so that losing them can never brick future updates.
17. As the maintainer, I want the CI signing secret to hold the canonical key, so that the tag-triggered build signs with the same identity as local builds.
18. As the maintainer, I want the release procedure documented (README + workflow), so that v1.2 and later follow the same repeatable path.
19. As the maintainer, I want the first-release migration risk called out explicitly, so that the 10 existing users are guided rather than left to guess.

## Implementation Decisions

- **Package identity is frozen.** `applicationId = com.slukhayka.audiobooks`
  becomes permanent. This is irreversible (and later required for Play Store);
  the old `com.aistudio.audiobook.read` identity is retired.
- **Version.** `versionCode = 2`, `versionName = "1.1"`. `versionCode` must grow
  monotonically; this is the first release of the new package but continues the
  Слухайка line, so it is 2, not 1.
- **Artifact naming.** The release APK is `slukhayka-v1.1.apk` with a companion
  `slukhayka-v1.1.apk.sha256`. The rename is applied consistently in the Gradle
  output naming, the release workflow, and the README install instructions (all
  three currently reference `app-release.apk`).
- **Single canonical signing key.** The local `my-upload-key.jks` (CN=Slukhayka,
  C=UA, SHA-256 fingerprint recorded at generation) is the canonical key for the
  whole future of the package. The CI `KEYSTORE_BASE64` / `STORE_PASSWORD` /
  `KEY_PASSWORD` secrets are overwritten with this same key so local and CI
  builds sign identically. The key and `keystore.properties` are backed up before
  tagging — losing them means the app can never be updated again under this
  signature.
- **Release mechanics.** Release goes through the existing tag-triggered
  workflow (`v*` → signed APK → GitHub Release with SHA-256). `v1.1` is tagged
  only after the code changes are merged and the CI secret is updated.
- **Release notes are human-written, not generated.** `generate_release_notes`
  stays disabled; the release body is a short «що нового» list plus a mandatory
  migration block stating: new package, installs alongside the old app, books
  must be re-imported, progress/downloads/history do not transfer, and the old
  app can be deleted.
- **No runtime code changes.** This release changes only build/release
  configuration and documentation; it introduces no schema change, no new
  module, and no new runtime seam. All shipped behavior already exists on `main`.
- **No new test seams.** Verification happens at the highest existing seams
  (artifact, JVM suite, lint, CI workflow, on-device smoke); no new runtime
  seams are added.

## Testing Decisions

- **What makes a good test here:** assert external, observable behavior — the
  properties of the built artifact and the green-ness of existing gates — not
  internal implementation. For a release spec, the "behavior under test" is the
  artifact itself.
- **Artifact seam (the one new seam).** The `assembleRelease` output is verified
  as: filename is `slukhayka-v1.1.apk`; `package = com.slukhayka.audiobooks`;
  `versionCode = 2`; `versionName = 1.1`; signing certificate SHA-256 equals the
  canonical key (via `aapt2 dump badging` and `apksigner verify --print-certs`).
- **JVM seam (existing).** `:app:testDebugUnitTest` (Robolectric + Roborazzi,
  with the Kover 80% instruction / 70% branch gate) must pass.
- **Static-analysis seam (existing).** `:app:lint` must pass.
- **CI seam (existing).** The `v1.1` tag run itself is the test of the workflow:
  it must produce the release with the APK + SHA-256 + release notes (verified
  after the run via `gh release view`).
- **On-device seam (manual).** A fresh-install smoke on the maintainer's phone
  using the final signed APK: install → first-run → import a book from a source →
  playback → sleep timer → download a book → offline (airplane mode) → widget.
- **Prior art.** The JVM suite is the same one run today; the artifact-seam
  verification is new but trivial and scriptable. The single instrumented
  Espresso test (`AudioPlaybackEspressoTest`) is NOT part of this release's gate.

## Out of Scope

- **Screen-size / orientation adaptability** (foldables, tablets, landscape,
  multi-window): deferred to **v1.2**.
- **In-app update check** («доступна нова версія»): deferred to **v1.2**.
- **Play Store publishing** and Play In-App Updates (requires store listing,
  not side-load).
- **Data migration / sync** between the old `com.aistudio.audiobook.read`
  install and the new package (impossible across packages; device sync arrives
  later, not now). Migration is manual and one-way.
- **Auto-generated release notes** from commits.
- **Espresso instrumented test** in the pre-release gate.

## Further Notes

- The 10 existing users are on `com.aistudio.audiobook.read` (v1.0). This
  release is a fresh install for them, not an in-place update; the migration
  block in the release notes is a hard requirement, not polish.
- The old v1.0 package and its signing key are retired; the CI keystore secret
  should be replaced with the canonical key, not kept in parallel.
- Keystore loss is unrecoverable — the backup step is a hard prerequisite
  before tagging `v1.1`.
- The follow-up (v1.2: adaptability + update check) is a separate spec and will
  get its own grilling and test seams.
